# 040 — wp4 ship

Runs after the three repo ledgers close.

## What ships

1. **Issues.** One per new case on lidge-jun/fuck-powershell, in the established
   schema, then cross-linked into the case `refs` and CLOSED with a registration
   comment naming the case file and its live page. That is the convention issues
   1-40 already follow, and it is what keeps the tracker at zero open.
2. **Counts.** README states the corpus size and the ontology totals in three
   places; all must agree with `find cases -name '*.md' | wc -l` and the
   `validate-graph` output. The site index counts are generated by
   `sync-cases.mjs` and need no hand editing.
3. **Skill.** `build-skill` regenerated so the installable skill's reference
   tables match the corpus.
4. **Push and verify.** Push to origin main, confirm the Pages deploy succeeded at
   the pushed SHA, and fetch at least one new case page expecting 200.

## Ordering

Issues first, because cross-linking edits the case files that the counts are
computed from. Push last.

## Acceptance

- Zero open issues on the repo after the round.
- README count, site count, and the file count all agree.
- validate-graph reports 0 violations over the whole corpus.
- Pages deploy green at the pushed SHA; a new case URL returns 200.

## Provenance note for the round

This is the first round whose cases come from repositories this project does not
own, and the first to admit open issues as evidence. The devlog should say so
plainly: a reader six months from now should be able to tell which cases were
mined from first-party history, which from upstream projects, and which from
vendor documentation, because those three have different failure modes and
different staleness risks.
